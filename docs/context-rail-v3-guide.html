Context Rail v3 · visual guide

One store. Five rules. Any tool does the work.

Context Rail is a project workspace where Markdown files are the truth, an SQLite index is only a cache, and the work happens in whatever coding tool you already use, inside gates a human sets.

01 · Overview

What it is, in one picture

The project lives in files. A cache makes reading them instant. One pipeline makes changing them safe. Agents and humans use the same commands — the difference is what each one is allowed to do.

1source of truth: the store
3surfaces: CLI, MCP, web UI
6primitives, never renamed
4speed budgets in CI

📁 Files are the truth

Every document is a Markdown file with a small frontmatter block. Commit it, diff it, edit it by hand. Nothing important lives only in a database, and no agent has a private memory that other agents cannot see.

⚡ The index is a cache

SQLite mirrors the files so the CTO views are fast at ten thousand documents. Delete the index and the next command rebuilds it. Reads never hash a source tree and never execute a command.

🚪 One write path

Every change — from the CLI, an MCP client or the web UI — goes through the same pipeline: validate, authorize, lock, write, record, index. There is no second way to mutate the store.

✂️ Agents get slices

The CTO gets a bounded brief. An implementer gets a work order and a narrow scope. A reviewer gets a candidate commit. Nobody loads the whole project into a context window.

Truth on the left, speed on the right

context-rail/ truth

  • rail.yaml — placement and pack
  • charter.md — gates, rights, budgets
  • items/, notes/, checks/
  • records/ — candidates, reports, verdicts, approvals
  • workspace/ — agent prompts, skills, memory

Committed to git. Editable by hand. Survives every tool.

One-way: files → index. Never the other way.

Why this matters You can stop using the tool at any time and still have a readable, reviewable project. The database is disposable; the project is not.
02 · System map

Every command takes the same path

One entry point, one decision layer, one write door and one read door. Handlers describe what should happen; they never touch a file directly.

Gateway

The only front door. Refuses unknown tools, bad parameters and forbidden actors before any work starts.

Kernel

The rulebook: what is executable, blocked, stuck, too long, or allowed. Pure, so it can be tested exhaustively.

Write pipeline

Serializes changes with a store lock, checks the expected revision, writes atomically and appends a record.

Checks

The rail runs the commands an item declares, and only when asked. Hard timeouts, capped output, scrubbed environment, secret redaction in verdicts.

03 · Data model

Behavior comes from structure, not from names

Six primitives, eight relation names and five lifecycle categories. The engine never reads a status name or a tag; packs map their own words onto these fixed categories.

Solid arrows mean “this document points at that one”. The dashed arrow is the one that can block work: an unfinished depends_on target makes an item non-executable.

Primitives

item note record check actor policy

Item = something that can be done. Note = knowledge. Record = an immutable fact. Check = a provable condition. Actor = who acts. Policy = what is allowed.

Relations

part_of depends_on verifies about because_of supersedes resolves owned_by

Fixed names. A pack can add presets and tags, never new engine relations.

Categories

not_started active blocked done dropped

Packs name their own statuses; each maps to one of these. The engine only ever reads the category.

What one document looks like

---
primitive: item
preset: task
title: Write the first task
status: todo
part_of: ["[[ship-v3]]"]
depends_on: ["[[design-the-api]]"]
tags: ["small"]
created: 2026-11-01T09:00:00Z
updated: 2026-11-01T09:00:00Z
---

# Write the first task

The body is ordinary Markdown. It can be as long as
the work needs; the brief reads only what it must.
primitiveWhat kind of thing this is. Fixed by the engine.
presetThe template that produced it. Packs define presets.
statusA pack word that maps to a category, so the engine can reason about it.
relationsLinks by slug. part_of builds the tree; depends_on builds the order.

Executable

A leaf item in a workable category with no unfinished dependency.

Blocked

Category blocked, or a dependency that is not finished.

Stuck

An active item with no new record inside the stuck window.

Too long

The item's recorded attempts or elapsed time exceed its budget. It shows up as a wait for the human; nothing is refused.

04 · One command, start to finish

Six steps, then one envelope

A command is not a script with side effects. It is a request that either produces a validated change or a typed refusal — never a half-written file and never a traceback.

1InputThe surface passes typed arguments from the tool table.
→
2ValidateRequired fields, types and bounds. Unknown keys are refused.
→
3AuthorizeThe actor and the charter decide if this call is allowed.
→
4HandleThe handler asks the pure kernel what the new state should be.
→
5CommitLock, expected revision, temp file, fsync, atomic replace, record.
→
6AnswerThe index catches up; the caller gets one JSON envelope.

A real call

$ rail change add task "Write the first task" --rel part_of=ship-v3

{
  "ok": true,
  "value": {
    "slug": "write-the-first-task",
    "path": "items/task/write-the-first-task.md",
    "etag": "22686e95ed738d95",
    "record": "01M6AV2B03HBQ076BRZJXCNFCC"
  }
}

Exit codes

0 success · 1 refusal · 2 infrastructure failure. Scripts can branch on these.

Idempotency keys

Every write takes --key. Sending the same candidate or hook again returns the same record instead of duplicating it.

Expected revision

Updates carry the etag they read. A stale write is refused, never silently overwritten.

05 · Who decides

Three rings of permission

The charter is the human's contract with the agent. It turns “the agent can do anything” into three concrete rings, enforced at the gateway for every command.

🟢 CTO alone

Break work down, order it, hand a brief to a tool, refactor, write tests, run a check, close an item when its gates pass. This is the daily autonomy.

🟡 CTO decides, reversible

New dependencies, data-model or API changes, convention changes, dropping a could-have, spending near a budget. The digest lists these so the human can see them and reverse them.

🔴 Human only

The goal, must/should scope and the Won't list; writing or loosening acceptance checks; publishing, deploying, deleting data, force-push, tags and releases; licensing, secrets and payments; budget increases; stuck items that no tool could finish; changing the charter.

Approval is a typed phrase

The tool never asks “are you sure?”. It asks for a phrase that names the exact target:

rail --actor human approve charter \
  --confirm "APPROVE charter" \
  --confirmer "Ada"

The approval is a record with the hash of every protected file, and it names its signer: a human by default, or a named lead signing on the human's behalf when the charter allows it (approval.agents: true, the default; set approval.agents: false in the charter to require a human signature). If a protected file drifts, doctor and ci fail.

Until approval, nothing executes

Anyone can plan, read and draft. A candidate, a check run, a review and a move into an active or done category refuse with “the charter is not approved; nothing executes yet”.

Why so strict? The charter is where a human sets the quality bar and the boundary. An agent that can rewrite its own boundary has no boundary.
06 · The record loop

One item, six moves

The rail keeps no state beyond the store, and it never launches an agent. Every item is: read the work order, work in your own tool, record the candidate, prove it, review it, move it, report it. The rail holds the order, the proof and the record; your tool does the work.

The blue node starts each pass and the yellow note is the human view. Everything between them happens in the tool you already use, inside the charter's green and yellow rings.

Brief

The work order for one item: objective, selected scope, conventions, constraints, files, checks and the focus breadcrumb. Read-only.

Work and record

The agent works in its own checkout with its own sub-agents, commits, then records that commit as an immutable candidate.

Prove

The item's declared checks run on demand. A check is fresh only while its definition and its inputs still match.

Review, then move

A different actor judges one commit, so a review of an older commit is stale. The move is the record that the work is accepted.

When an attempt fails Nothing tries again for you. The agent decides in its own tool whether to try again or to report the failure, and the attempt is recorded with its evidence. The rail never starts work on its own and never raises a failed attempt to the human on a timer.
07 · From zero to daily

The first hour, then the routine

You can start with a goal and a task; you do not need the whole record loop on day one. The store and its views are useful immediately.

  1. Step 0 · 2 minutes

    Install

    py -m pip install context-rail

    You now have rail, ctx-rail and py -m context_rail.

  2. Step 1 · 1 minute

    Create the store

    rail init --pack basic --scaffold

    Packs by workflow: basic (one stream), flow (continuous kanban), scrum (sprints), waterfall (phase gates), video (scenes and shots), portfolio (cross-project coordination across child stores) and adaptive-contract (risk-tiered changes with proportionate verification). small and indie still resolve to basic and flow for existing stores. This walkthrough uses --scaffold so each step stays visible; bare rail init --pack basic runs the full resumable pipeline, including the picture offer, approval, agent files and optional git drivers. A guided picture is rail init --interview or --answers-file; a CTO draft is --draft-file.

  3. Step 2 · 10 minutes

    Draw the picture

    rail change add goal "Ship v3"
rail change add task "Write the first task" --rel part_of=ship-v3
rail read status

    Goal → scope → tasks → checks. Relations do the structure; tags are only for humans.

  4. Step 3 · the boundary

    Approve the charter

    rail --actor human approve charter --confirm "APPROVE charter" --confirmer "Ada"

    This is the moment the human hands over autonomy. Until then anyone can plan and read, but no candidate, check, review or move executes.

  5. Step 4 · first work

    Brief, work, record

    rail loop brief write-the-first-task --role implementer
# the agent does the work in its own tool and commits
rail loop candidate write-the-first-task --commit <sha>

    Then rail check run write-the-first-task --worktree <path>, rail loop review <item> --commit <sha> --verdict approve and rail change move <item> <status> --expect <etag> --key ….

  6. Step 5 · daily

    Read, then hand out the next brief

    rail overview
rail loop brief <item> --role implementer

    There is no scheduler. You or your tool ask for the work order, and the rail answers with one item at a time.

  7. Step 6 · weekly

    Hygiene and the ledger

    rail read digest
rail read ledger
rail loop triage
rail gate
rail ops doctor
08 · A day with the rail

What your tool does, what you do

The rail is built so the human's attention is spent on boundaries and taste, not on relaying context between agents.

🤖 Your coding tool

  • Reads the brief for one item and its selected scope.
  • Works in its own checkout with its own sub-agents and models.
  • Commits in its own checkout, then records the commit as a candidate.
  • Runs the item's checks and records the verdicts.
  • Hands the candidate to a different actor for review.
  • Files a report for what happened, even when nothing did.

🧑 You

  • Read rail overview — two minutes, not two hours.
  • Answer needs_human: approvals, reviews, waits.
  • Read rail read digest for reversible decisions and quality.
  • Approve the irreversible few: scope, secrets, releases, budgets.
  • Spot-check one accepted item when something feels off.

Morning

rail overview → what is executable, what waits, what is stuck, what drifted.

During the day

rail loop brief <item> → the next work order. You answer only the waits the digest names.

Evening

rail read digest → counts, quality, usage, and the reversible decisions you may want to undo.

What “human in the loop” actually means You are not asked to review every diff. You are asked to own the goal, the acceptance bar, the secrets, the money and anything irreversible. Everything else is delegated on purpose.
09 · Where everything lives

Three places, three jobs

The store is portable. The index is disposable. The control files are machine-local and survive a crash. 

my-project/
├── context-rail/              ← the store: the truth, commit this
│   ├── rail.yaml                  placement, pack, schema
│   ├── charter.md                 gates, rights, budgets
│   ├── project/  items/  notes/  checks/
│   ├── records/2026-11/           candidates, reports, verdicts, approvals
│   └── workspace/                 cto + profile prompts, skills, memory
└── .git/
    └── context-rail/            ← index cache: disposable, never commit

Outside a git worktree, the index and control files live in:
context-rail/.rail-local/      ← index, locks, write intents, idempotency results

📁 Store truth

Markdown plus YAML. Diffable, mergeable, hand-editable. The only thing worth backing up.

⚡ Index cache

Rebuilt from files when missing or corrupt. Deleting it costs one rebuild, never data.

🔒 Control files machine-local

Proof that a write landed: the store lock, the pending intent, and the idempotency result for each key. Written atomically.

Editing by hand is allowed Change a Markdown file in your editor; the next command stat-scans the store and updates the index. Use the CLI when you want validation, records, idempotency and the one write path.
10 · Rules that never bend

The invariants behind the safety story

These are not conventions. They are the reasons the system can be trusted with work recorded by an agent you did not watch.

🚪 One write path

Every mutation goes through store.write.commit. No handler, no check and no UI writes store files on its own.

👀 Reads are side-effect free

No read executes a command or hashes a source tree. A read can be slow, never dangerous.

🧠 Pure kernel

kernel/ has no file, git, process or index access. Rules are exhaustively testable.

🔒 Fail closed

An unknown manifest schema, pack version, key or policy field is refused, never guessed.

⏮️ Stale is refused

Every change carries the revision it read. Optimistic concurrency, never a silent overwrite.

🛟 Crash safety

Temp file, fsync, atomic replace. An intent marker covers multi-file writes; rail ops repair finishes or rolls back.

Speed budgets are tests, not hopes

Operation1,000 documents10,000 documents
CLI startupunder 150 msunder 150 ms
Warm read (cto brief, status)under 300 msunder 1 s
Cold rebuildunder 10 sunder 60 s
Single writeunder 200 msunder 200 ms

If a change needs more time, the change is the bug. The budgets are never raised.

12 · When something goes wrong

Typed refusals, not tracebacks

Every failure is one JSON envelope with a code. The most common first-run bumps:

MessageWhat it meansFix
NOT_FOUND: no store found You are not inside a project, or the folder has no rail.yaml. rail init, or pass --store before the command.
VALIDATION_FAILED: unrecognized arguments Options are in the wrong place, or add got flags instead of positionals. rail --store X add task "Title", not rail change add --preset ….
approval_mismatch A protected file changed after it was approved, so the pack and the approval no longer agree. Review the diff, then reapprove (a named lead may sign when the charter allows it): rail approve charter --confirm "APPROVE charter" --confirmer "…".
“the charter is not approved; nothing executes yet” The approval gate has not been passed. rail approve charter --confirm "APPROVE charter" --confirmer "…" (add --actor human for a human signature).
A check reports stale The files the check declares have changed since its verdict. Re-run rail check run; a stale pass is not a pass.
The index looks wrong The cache drifted or was interrupted. rail ops reindex, or delete the index and let it rebuild. Never touch the store.

Safe recovery order

  1. Read the code in the envelope.
  2. rail ops doctor for integrity.
  3. rail ops reindex if reads disagree with files.
  4. rail ops repair for an interrupted write.
  5. Only then touch files by hand.

What you never need to do

  • Hand-edit the SQLite index.
  • Re-run a write to “make it stick” — use the same --key.
  • Delete the store to fix a view.
  • Raise a speed budget.
