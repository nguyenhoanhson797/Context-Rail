01 · architecture

Every surface, one engine.

The CLI, the MCP server and the loopback UI are generated from one tool table. The gateway validates and authorizes before a handler runs. The kernel is pure. The write pipeline is the only thing that mutates files, and the index is a disposable cache.

39 tools · 1 gateway · 1 write path

Files are the truth

A project is a context-rail/ folder of Markdown and JSON plus rail.yaml, committed to git and editable by hand. The index is not the product.

The kernel is pure

Lifecycle, structure, gates, rights, budgets and measurement are functions over primitives. No file, git, process or index access, so the rules can be tested exhaustively.

Reads never run code

Reads are SQL against the index. They never execute a command or hash a source tree. A stale or corrupt index is rebuilt, not trusted.

02 · vocabulary

Six primitives. Nothing else.

A primitive is a shape the engine understands. Presets such as goal, task or sprint are only tags plus a template and defaults. Tags are free text. Engine logic never branches on either one.

01 · primitive

Item

Anything with a lifecycle that can be done. One primitive covers goals, scopes, tasks, milestones, sprints, risks, questions and fixes.

goalscopetaskmilestonesprintriskquestionfix

Affects the project by: driving executable work, dependencies, blockers, stuck and too-long detection, and score rollup through part_of.

02 · primitive

Note

Knowledge with no lifecycle: conventions, architecture, plans, skills and memory. It informs work without becoming work.

noteconventionvisionwontskill

Affects the project by: feeding context recipes and generated agent skills. It never appears as executable work.

03 · primitive

Record

An immutable, append-only fact: a decision, run, verdict, report, approval or status change. History is appended, never rewritten.

decisioneventrunverdictreportapproval

Affects the project by: providing the ledger, the audit trail, replay, triage and measurement. Every change leaves one.

04 · primitive

Check

A verifiable condition with a verdict and a freshness state. A Check can target one Item; only a linked, fresh pass gates work.

cmdexistsevidencereviewhuman

Affects the project by: gating item_done, scope_done, merge and release. A stale pass is not a pass.

05 · primitive

Actor

Who acts: the human, the CTO, the implementer and the reviewer. A profile narrows methods, context and budget.

humanctoimplementerreviewer

Affects the project by: enforcing permissions, method narrowing, review separation and the actor stamped on every Record.

06 · primitive

Policy

The rules of the project: charter.md with gates, decision rights, budgets, thresholds and the change rule.

chartergatesrightsbudgets

Affects the project by: bounding every decision. Protected files are approved by hash; nothing executes before approval.

03 · wiring

Eight relations connect everything.

Direction matters: a Check verifies an Item; an Item does not verify a Check. These eight names are the whole relation vocabulary. Hover a row to trace the matching edge.

↔ drag the graph sideways to see all of it

RelationDirectionWhat it changes
part_of Item → Item The work hierarchy. A parent's score is the proven-over-total Checks of all its descendants; a parent is never an executable leaf.
depends_on Item → Item Ordering. An open dependency blocks execution; a dependency cycle is detected and reported.
verifies Check → Item Proof. A Check can verify one Item; only a fresh pass counts toward a gate.
about any → any Context. A Record, Note or report points at its subject without making a lifecycle claim.
because_of Item / Record → Record Causality. Triage links a fix to the reports that caused it; the digest can show why work exists.
supersedes Record → Record History. A newer decision replaces an older one without deleting it.
resolves Item → Record / Item Closure. A fix closes the reports or Items it resolves; measure fix follows these edges.
owned_by any → Actor Ownership. The Actor's profile decides allowed methods, context recipe and budget.

Only these eight names exist. part_of and depends_on make the work graph; verifies makes the proof graph; about, because_of, supersedes and resolves make the memory graph; owned_by attaches documents to an Actor.

Transitions are declared, not guessed. In basic: todo → doing | dropped, doing → blocked | done | dropped | todo, blocked → doing | dropped, done → doing, dropped → todo. Any other move is refused with the allowed list.

05 · mutation

One write. Eight guarantees.

Every change — CLI, MCP, UI, dispatch, merge, migration — enters store.write.commit. The order is fixed. A crash leaves a witness, not a half-written store.

01

Validate & authorize

Parameters, actor, permission, decision class and charter approval are checked before a handler runs.

gateway.invoke()
02

Lock

One store lock for one writer. Concurrent writers queue; a CTO tick also holds a single-instance lock.

store_lock()
03

Expect

Compare the etag the caller read with the current one. A stale revision is refused, never silently overwritten.

expect = etag
04

Intent

A durable marker is published before a multi-file write, so recovery can prove what was in flight.

intents/
05

Stage & fsync

Bytes go to temp files, are flushed, then atomically replace their targets in order.

temp + fsync + replace
06

Record

An immutable, digest-stamped Record is appended. The idempotency key makes a retry return the same record.

records/<yyyy>-<mm>/<id>.json
07

Index

The SQLite cache catches up while the write is still inside the lock. Reads never hash the source tree.

index.sync()
08

Return

Unlock and return one typed Result envelope. A failure is a code and message, not an exception at the boundary.

{ ok, value } | { ok, error }

Read left to right, then the next row. Every step happens inside one lock and one write path.

If it crashes after step 04

The intent is the witness. The next write or rail doctor --repair rolls the operation forward when it can prove the targets are safe; anything unprovable is kept and reported. Nothing is guessed.

If the write is refused

A stale etag, a path escape, an unknown schema, an unapproved charter or a human-only decision stops before any handler runs. Refusals write nothing.

Optimistic concurrencyEvery update carries the revision it read.
IdempotencyEvery write has a key; a retry returns the same record.
Atomic replaceTemp file + fsync + replace, never an in-place edit.
Path confinementStore paths only; adapter files are the one declared exception.
RepairableIntent marker + doctor --repair, with a report when unsure.
FastOne write under 200 ms at 1k and 10k documents.

06 · the agent loop

One tick, eight steps.

Brief → plan → dispatch → verify → review → merge → report → digest. The CTO keeps no state between ticks beyond the store and its memory Notes. Humans look at the brief and the digest; everything between runs inside the charter's rights, gates and budgets.

read / human-facing CTO work learning enforced gate: dispatch approval, review separation, merge policy
StepCommandWhat it gives you
01 Briefrail cto briefApproval state, goal and scope, gate rules, executable work, human waits, quality and reversible decisions, inside a character budget.
02 Planrail add · rail linkItems with part_of and depends_on edges. Writing or loosening acceptance Checks is human-only.
03 Dispatchrail dispatch <item> --expect <etag> --key <k>A fresh worktree and branch, a bounded droid exec, a run Record, then verification. Refused before charter approval.
04 Verifyrail verify <item>The Item's declared Checks run in the worktree. A cmd pass is fresh only while its input blobs match.
05 Reviewrail review <item> --run <id> --key <k>A different actor in its own worktree. The implementer cannot approve its own work; the verdict binds to the candidate commit.
06 Mergerail merge <item> --run <id> --expect <etag> --key <k>Rebase, then fast-forward. One conflict retry, then escalate. --push only when the charter allows it.
07 Reportrail report ... --report-file <json>One structured report per completed run: target class, expectation, observation, impact, evidence. “Nothing to report” is valid.
08 Digestrail digest · rail triageActivity, waits, reversible decisions, stuck and too-long Items, quality and usage. Triage clusters reports into fixes, proposals or engine issues.

One retry, then escalate

A failed implementer run gets one retry that continues the same droid session with the failure output. Still failing means a human sees the evidence, not an infinite loop.

One rebase, then escalate

A merge conflict gets one rebase retry. If it still conflicts, the candidate and diagnostics are kept for the human; nothing is force-pushed.

07 · from zero

From an empty folder to a daily loop.

This is the order the commands are designed to be used in. Steps marked HUMAN are decision points, not suggestions. Every --key is idempotent; every --expect is the etag you just read.

01
any actor

Install

py -m pip install context-rail

Python 3.11+. Installs rail and ctx-rail; py -m context_rail is equivalent. Reading and editing a store needs no droid.

02
any actor

Create the skeleton

rail init --pack basic --scaffold

Writes context-rail/rail.yaml, .gitignore and the pinned empty folders. Bare rail init instead runs the full resumable pipeline: skeleton, workspace seed, picture offer, approval, agent files and optional git drivers.

03
human

Onboard the picture

rail init --interview
rail init --answers-file answers.json --confirm "APPROVE charter"

Produces the goal, vision, Won't list and must/should/could scope, plus charter.md, the three profiles and the pack's skills. A CTO may only propose with --draft-file, and a draft records no approval.

04
human

Approve the boundary

rail --actor human approve charter --confirm "APPROVE charter" --confirmer "Ada"

Records the approval with hashes of the protected files. Until this exists, the CTO may plan and read, but nothing executes.

05
any actor

Make the checkout agent-ready

rail adapters sync

Writes the managed AGENTS.md block and one .agents/skills/<name>/SKILL.md per skill Note. Optional harnesses: Claude, Cursor and Gemini. Re-run when a skill changes.

06
any actor

Shape the work

rail add goal "Ship v3"
rail add scope "Core engine" --set priority=must
rail add task "Write the write path" --rel part_of=core-engine

Items are placed by rail.yaml. part_of builds the hierarchy; depends_on sets the order.

07
any actor

Declare the proof

rail check write-path --target write-the-write-path --spec-file check.json --expect absent
rail verify write-the-write-path

Pick a mode: cmd, exists, evidence, review or human. A stale pass is not a pass; writing or loosening acceptance Checks is human-only.

08
any actor

Read the state

rail status
rail cto brief

Counts, executable leaves, blockers with reasons and stuck Items; then the bounded CTO page with approval, gates, executable work, human waits and quality.

09
CTO

Dispatch one leaf

rail dispatch write-the-write-path --expect <etag> --key day-1-a

A fresh worktree and branch, a bounded droid exec, a run Record, then the Item's Checks verify the candidate. Not executable if it is a parent, blocked or still depends on open work.

10
CTO

Review the candidate

rail review write-the-write-path --run <run-id> --key day-1-b

Must be a different actor and worktree. The implementer cannot approve its own work; the charter may also require a different model.

11
CTO

Merge the proof

rail merge write-the-write-path --run <run-id> --expect <etag> --key day-1-c

Rebase, then fast-forward. One conflict retry, then escalate. --push only when the charter allows it.

12
human + CTO

Learn, close, repeat

rail report --run <run-id> --report-file report.json
rail triage
rail digest
rail ci

One report per run. Triage turns clusters into fixes, proposals or engine issues. Digest shows what is stuck or too long. CI gates approval and done gates, never a Check run.

08 · authority

Who may decide what.

The gateway checks this before a handler runs. A profile can narrow a role's methods; it can never widen the human-only floor or the change rule.

green · CTO alone

Runs the work

  • Break down, order and assign work.
  • Technical design inside the conventions.
  • Refactors and tests.
  • Retries.
  • Close Items when their gates pass.
yellow · CTO decides, reversible from digest

Moves the boundary carefully

  • New dependencies.
  • Data-model or API changes.
  • Convention changes that come from reports.
  • Dropping Could-have Items.
  • Spending near the budget.
red · human only

Owns the irreversible

  • The goal, must/should scope and the Won't list.
  • Writing or loosening acceptance Checks.
  • Product taste.
  • Publishing, deploying or deleting data.
  • History rewrites, force-pushes, tags and releases.
  • Licensing, secrets and payments.
  • Budget increases.
  • Stuck Items after their retries.
  • Charter changes. The change rule can never be delegated.
Approval is detection, not prevention. Hand edits are allowed. Doctor and CI compare protected files with the approval hashes, so an unapproved edit fails the gate. This catches drift, not a deliberately forged approval.

09 · reference

Store map and tools.

The store is a normal folder in git. The index and control files live outside the repository tree. Every command in the table below is generated from the same 39-tool tuple. 

context-rail/              # default root, committed
├─ rail.yaml               # schema 3 · pack · placement
├─ charter.md              # policy: gates · rights · budgets
├─ project/                # goal · vision · scope · wont
├─ items/<preset>/         # Item Markdown
├─ notes/<preset>/         # Note Markdown
├─ checks/                 # Check specs
├─ records/<yyyy>-<mm>/   # immutable JSON + decision .md
├─ workspace/
│  ├─ cto/profile.md
│  ├─ profiles/<name>/profile.md
│  └─ skills/<name>.md
├─ packs/<name>/           # local packs
└─ .gitignore

Where the index lives

<git-dir>/context-rail/<key>/index.sqlite3 inside a worktree; <store>/.rail-local/ outside git. Never in the repository tree. Delete it and the next command rebuilds it.

Where control files live

Write intents, idempotency results, locks and dispatch/tick progress sit in the same local dir. They are written atomically, so a crash leaves the old file or the new one, never a partial document.

What is generated outside the store

AGENTS.md, .agents/skills/, and optionally CLAUDE.md, .cursor/rules/ and GEMINI.md. They embed the store's profiles and skills; they are not a second source of truth.
