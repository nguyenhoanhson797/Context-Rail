# Harness wiring

The rail is harness-agnostic. Every harness gets the same thing:

1. **An instruction file** it reads automatically.
2. **A way to call the rail** — CLI, or MCP for a tool-calling client.
3. **An actor** that matches the session's rights.

The server command is the constant:

```bash
rail --store context-rail --actor cto serve mcp
```

Use an absolute `--store` if the harness starts outside the project root. Omit
`--store` when the process starts inside the project and the nearest
`context-rail/` folder should be used.

## The universal instruction file

Copy [`AGENTS.template.md`](../AGENTS.template.md) into the project root as
`AGENTS.md`. It is written for any
agent and any harness. If the harness uses a different filename, keep the
content and change the name (see the table below).

The rail can also render managed copies for the common harnesses:

```bash
rail ops adapters render                              # AGENTS.md + .agents/skills/
rail ops adapters render --harness claude --harness cursor --harness gemini
```

That writes `CLAUDE.md`, `.claude/agents/<role>.md`,
`.cursor/rules/context-rail.mdc`, `GEMINI.md` and one
`.agents/skills/<name>/SKILL.md` per workspace skill. The managed block is
marker-delimited and digest-checked; prose outside it is preserved.

## The universal MCP descriptor

Most clients accept a JSON server entry with these three fields. The exact file
and top-level key vary; the `command`/`args`/`env` shape does not.

```json
{
  "mcpServers": {
    "context-rail": {
      "command": "rail",
      "args": ["--store", "context-rail", "--actor", "cto", "serve", "mcp"],
      "env": {}
    }
  }
}
```

On Windows, if `rail` is not directly executable from the client, use the
interpreter form:

```json
{
  "mcpServers": {
    "context-rail": {
      "command": "py",
      "args": ["-m", "context_rail", "--store", "context-rail", "--actor", "cto", "serve", "mcp"]
    }
  }
}
```

The MCP server exposes the **canonical** tool names (`status`, `next`, `show`,
`add`, `move`, `dispatch`, `review`, `merge`, …), each with a closed JSON schema
and a `permission`/`decision` metadata pair. The response is the same JSON
envelope as the CLI: `{"ok": true, "value": ...}` or `{"ok": false, "error":
{...}}`.

## Actor choice

| Session | Launch with | Why |
|---|---|---|
| Read-only exploration | no actor, or `--actor cto` | MCP defaults to `cto` |
| Normal agent work | `--actor cto` or a worker name | writes are attributed |
| Human approval session | `--actor human` | `approve`, `ops migrate`, `ops pack use` are human-only |
| Separate reviewer | `--actor reviewer` | separation from the implementer |

The actor is a **workflow claim**, not authentication. It records who acted and
enforces the charter's rights. Anyone with shell access as your OS user can act
as you; use OS-level isolation for a real boundary.

## Per-harness notes

### Claude Code

- Reads `CLAUDE.md`, `AGENTS.md`, `.claude/skills/<name>/SKILL.md` and
  `.claude/agents/<role>.md`.
- MCP: `.mcp.json` at the project root, or the user-level MCP config, with the
  `mcpServers` descriptor above.
- The rail can generate `.claude/agents/{cto,implementer,reviewer}.md` from the
  store's profiles: `rail ops adapters render --harness claude`.
- Use a distinct `--actor` for review so the implementer cannot approve its own
  work.

### Cursor

- Rules: `.cursor/rules/context-rail.mdc` (generated by the rail with
  `--harness cursor`), or `.cursor/rules/*.mdc`.
- MCP: `.cursor/mcp.json` (project) or the global MCP settings, using the
  `mcpServers` descriptor.
- Cursor is a good fit for the UI: `rail serve ui` opens the same compiled
  snapshot in a browser without an agent in the loop.

### Gemini CLI

- Reads `GEMINI.md` and skill files.
- MCP: the CLI's settings file (`settings.json`) with an `mcpServers` entry.
- Generate the instruction file with `rail ops adapters render --harness
  gemini`.

### OpenCode

- Reads `AGENTS.md` and skills from the configured skill directory.
- MCP: add the descriptor to the OpenCode config (`opencode.json`) under its MCP
  section.
- Skills under `skills/` can be installed by copying
  `skills/context-rail-v3*` into the agent's skill directory.

### Codex

- Reads `AGENTS.md` from the repository root.
- MCP: add the server to the Codex config (`~/.codex/config.toml` or the
  project-level config) using its MCP server table; the command and args are the
  same.
- Codex sessions usually run as one actor per task; use `--actor` to name the
  role.

### Windsurf, Cline, Continue and other MCP clients

- Instruction file: use the client's rules file (for example a global rules file
  or a `.windsurf/rules` entry) and paste the contents of
  [`AGENTS.template.md`](../AGENTS.template.md).
- MCP: add the descriptor in the client's MCP settings.
- If the client cannot launch a stdio server, use the CLI directly; the CLI is
  the full surface, not a reduced one.

### No harness at all

Use the CLI. It is not a second-class path:

```bash
rail overview
rail next
rail read show <slug>
rail change move <slug> <status> --expect <etag> --key <key>
```

A shell loop is a valid agent. The loop is `overview → next → show → change →
check run → digest`.

## Skills vs instructions

| Mechanism | Best for | Where |
|---|---|---|
| `AGENTS.md` | always-on project rules | project root |
| Skill (`SKILL.md`) | on-demand operator knowledge | `.agents/skills/`, `.claude/skills/`, user skill dir |
| MCP | tool-calling with schemas | harness config |
| CLI | scripts, CI, humans, minimal harnesses | shell |
| UI | human review and tracking | `rail serve ui` |

Use more than one. The instruction file says *what not to break*; the skill says
*how to do a class of work*; MCP/CLI is *how to act*.

## A minimal wiring checklist

```text
[ ] rail installed and on PATH (or use py -m context_rail)
[ ] instruction file present at the harness's expected path
[ ] MCP server starts: rail --store <path> --actor cto serve mcp
[ ] the client lists canonical tools (status, next, show, ...)
[ ] the session actor matches the work (cto / worker / human)
[ ] rail types and rail next answer inside the session
[ ] a write with --expect and --key succeeds
[ ] rail ops doctor is clean
```
